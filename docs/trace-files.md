How traces are named, where large payloads live, and how many runs are kept together. Every SDK follows these rules, so a trace written by Node can be read by Python and the other way round. The content of a file is defined in [trace-schema.md](./trace-schema.md).

## One run, one file

A trace is one file holding one run. It is named after the run:

```
<run_id>.rootcast.json
```

The `.rootcast.json` suffix is how tools recognize a trace. Characters in `run_id` outside `A-Z a-z 0-9 . _ -` are replaced by `_` in the file name (`team/run 1` becomes `team_run_1.rootcast.json`). The `run_id` inside the file is never changed. Readers trust the field, not the file name.

Files are UTF-8, two space indented, LF line endings, with a trailing newline. Because SDKs agree on the exact bytes, a trace can be diffed, hashed and committed like source code. The repo's `.gitattributes` keeps `*.rootcast.json` LF on every platform.

## Where blobs live

Blobs live inside the trace, in its top level `blobs` map, keyed by `sha256:<hex>`. A step whose output is over 2048 canonical bytes stores `output_ref` and its payload sits in `blobs` under that key.

This keeps each file self contained. You can copy, attach or upload one file and nothing is lost. There is no separate blob directory in v0.1.

Anyone can check a blob, because its key is the sha256 of its canonical encoding. A trace with an `output_ref` but no `blobs` map is still valid, for example after a tool strips payloads before sharing, but readers will not have that output.

## Many runs: the trace store

When an agent runs many times, keep the traces together in a store:

```
.rootcast/                      store root
  runs/
    refund-7af3.rootcast.json   one file per run
    rag-21c9.rootcast.json
    tool-58d2.rootcast.json
```

* The store root is the `ROOTCAST_DIR` environment variable, or `.rootcast` in the working directory.
* Calling `save()` with no path writes to `<store>/runs/<run_id>.rootcast.json` and creates the folders.
* Saving the same `run_id` again overwrites that run. Give each run a unique id, for example a short random suffix.
* `runs/` holds trace files only. Other entries under the store root are reserved for later versions (replay results, indexes), so tools must ignore anything they do not recognize.
* `.rootcast/` is in `.gitignore`. Commit traces only when you want them as fixtures, like `examples/traces`.

| | Python | Node |
|---|---|---|
| Save to store | `rec.save()` | `rec.save()` |
| Save to a path | `rec.save("x.rootcast.json")` | `rec.save("x.rootcast.json")` |
| Store path of a run | `trace_path(run_id, root=None)` | `tracePath(runId, root?)` |
| List runs | list `runs/` | `listTraces(root?)` |
| Load and validate | `Trace.load(path)`, `validate(data)` | `loadTrace(path)`, `validateFile(path)` |
| CLI | `rootcast validate <file>` | `npx rootcast validate <file...>` |

## Cross language guarantee

The same scenario recorded from Python and from Node produces byte identical files. This is tested on every change:

* `examples/conformance/*.json` hold shared vectors (canonical bytes, hashes, validator messages) generated by `python examples/conformance/build_vectors.py`. Both test suites must reproduce them exactly.
* `examples/node/scenarios.mjs` ports the three sample scenarios to Node. The Node suite byte compares its output with `examples/traces`, and `packages/python/tests/test_crosslang.py` runs the Node recorder, then loads, validates and byte compares its files from Python.
